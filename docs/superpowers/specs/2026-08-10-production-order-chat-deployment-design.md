# Production Order Chat Deployment Design

## Goal

Prepare the existing long-running production deployment for the MoySklad order-chat feature without connecting to the production server, storing real credentials, applying a database migration, enabling the feature, or registering a webhook.

The preparation must preserve the current production topology and provide an explicit, reversible rollout path for PostgreSQL, Redis, NGINX, backend, frontend, Telegram notifications, and the new MinIO attachment store.

## Agreed boundaries

- The existing production server, service names, ports, and network layout remain authoritative.
- PostgreSQL, Redis, NGINX, frontend, backend, and the Telegram bot are not re-platformed.
- The backend keeps `network_mode: host` and reaches the published MinIO S3 endpoint at `localhost:9000`.
- MinIO is the only new production runtime service. It uses the existing pinned source build and a persistent named volume.
- No implementation or verification step contacts production services or external integrations.
- No real secret is written to a tracked file, command output, log, test fixture, or Docker image.
- The initial deployment keeps `ENABLE_MOYSKLAD_ORDER_CHAT=false`.
- Applying Alembic, enabling the feature, and registering the MoySklad webhook are separate manual operations that require production approval.

## Configuration artifacts

Add a tracked `.env.production.example` as the copy-and-merge reference for the server's existing ignored `.env`. It contains every setting required by the backend, existing integrations, order chat, MinIO, Compose, and the frontend build.

The example provides only non-secret production-safe values, such as:

- `APP_ENV=production`
- `ENABLE_MOYSKLAD_ORDER_CHAT=false`
- `MINIO_ENDPOINT=localhost:9000`
- `MINIO_BUCKET=pix-order-chat`
- `MINIO_SECURE=false` for host-local traffic
- the approved attachment and outbox defaults
- the public production API origin for `NEXT_PUBLIC_BACKEND_URL`

Credential-bearing values remain blank and are documented inline. The production operator merges only missing keys into the existing `.env`; replacing the whole server file is not part of the rollout.

The legacy misspelling `MOYSKLAD_PASWORD` is not included. Production uses `MOYSKLAD_PASSWORD` only.

## Production preflight

Add a non-mutating production preflight script. It loads the normal `Settings` boundary and validates configuration without printing secret values or contacting PostgreSQL, Redis, MinIO, MoySklad, Telegram, or any other external service.

The preflight has two modes:

1. Base deployment mode permits order chat to remain disabled but requires production-safe application, database, authentication, CORS, and frontend-build settings.
2. Order-chat mode additionally requires the feature flag, correctly named MoySklad credentials, Telegram notification configuration, a strong URL-safe webhook secret, valid MinIO credentials, endpoint and bucket settings, and positive attachment/outbox limits.

Failures identify only the variable name and validation rule. They never echo a value. The command returns nonzero on any failure so it can gate CI or an operator run.

Docker Compose interpolation is validated separately with the same ignored production `.env`. Validation does not start containers.

## Docker images and build context

The existing production Compose file remains the source of service topology. Its MinIO service keeps:

- source build pinned to `RELEASE.2025-10-15T17-29-55Z`;
- S3 and console ports `9000` and `9001`;
- a live healthcheck;
- the persistent `pix-minio-data` volume;
- credentials supplied only from the production environment;
- restart behavior suitable for the existing Compose deployment.

Backend startup depends on MinIO health where Compose supports conditional dependencies. The feature flag still protects the application from order-chat integration calls until the controlled enablement step.

Add backend and frontend `.dockerignore` files. They exclude at minimum `.env*` files other than tracked examples, Git metadata, virtual environments, dependency/build caches, test and browser artifacts, local database data, logs, and generated bytecode. This prevents the server's existing `.env` and the frontend's local `.env.local` from entering build layers.

The frontend Dockerfile accepts `NEXT_PUBLIC_BACKEND_URL` as an explicit build argument and exposes it to `next build`. Because this value is embedded in browser assets, passing it only through a runtime `env_file` is not considered sufficient. The value must be a public HTTPS origin ending in `/api_v1` and must contain no credentials, query parameters, or fragments.

The existing container names, published ports, and host-network behavior are preserved.

## CI deployment behavior

The current push deployment is unsafe for this rollout because it applies all Alembic revisions automatically, stops the full Compose project, and prunes Docker data. Change it so an ordinary code deployment:

1. updates the checked-out source;
2. runs the non-mutating production preflight in base mode;
3. validates Compose;
4. builds the required backend and MinIO images;
5. updates services with `docker compose up -d` rather than a full `down`/`up` cycle;
6. performs no database migration and no Docker prune.

The existing deployment authentication mechanism and GitHub secret names remain unchanged. Migration execution is deliberately excluded from the automatic workflow.

## Controlled rollout

The production runbook uses these checkpoints:

1. Confirm a restore owner, retention location, and tested commands for PostgreSQL and the MinIO volume.
2. Back up PostgreSQL before any schema change. If MinIO already contains data, back up it in the same retention set.
3. Merge the new environment keys into the existing server `.env` with order chat disabled.
4. Run base preflight and Compose validation without displaying the `.env` contents.
5. Deploy the code and images with `ENABLE_MOYSKLAD_ORDER_CHAT=false` and verify `/api_v1/health` plus existing product behavior.
6. Start MinIO, verify its health, write a disposable object, restart only MinIO, verify persistence, and remove only that disposable object.
7. Inspect the active database host and name without displaying its password, review `alembic history` and the order-chat migration SQL, then obtain explicit approval before applying revision `c8f2a4e6d901`.
8. Add the production MoySklad, Telegram, webhook, and MinIO secrets; set `ENABLE_MOYSKLAD_ORDER_CHAT=true`; run order-chat preflight; and restart only the backend.
9. Verify liveness, authenticated order-history access, attachment upload/download, Telegram side notification, immutable database triggers, ownership isolation, and two-tab realtime delivery.
10. Run webhook registration without `--apply`, review the redacted target, then obtain separate approval before the idempotent `--apply` invocation.
11. Verify a site message and attachment reach the matching MoySklad customer order, and a manager reply/file marked for the client reaches the correct site order.

The runbook contains commands but is not executed as part of this preparation task.

## Rollback

Incident rollback disables `ENABLE_MOYSKLAD_ORDER_CHAT` and restarts only the backend. It does not downgrade the append-only migration, delete order-chat tables, delete the MinIO volume, or remove canonical history.

Disabling or deleting the exact MoySklad webhook is a separate external mutation requiring approval. Existing general support chat and Telegram behavior continue independently.

## Error handling and observability

- Preflight failures are sanitized and actionable by variable name.
- NGINX keeps access logging disabled for the secret webhook path and preserves the order-chat upload-size route.
- Health verification uses the public backend liveness endpoint and MinIO's container healthcheck.
- Deployment and registration output never prints credentials or the webhook path secret.
- Order-chat runtime delivery failures remain in the durable outbox and existing Telegram projection-error channel.
- A failed rollout leaves the canonical PostgreSQL and MinIO data intact for investigation and retry.

## Verification

After implementation, run locally and after the final edit:

- backend `scripts/check.ps1`;
- frontend `npm.cmd run check` because its Docker build environment changes;
- base and order-chat preflight tests using synthetic values only;
- `docker compose config` with a temporary non-secret validation environment;
- backend and frontend Docker builds;
- a scan proving ignored `.env` files do not enter build contexts or image layers;
- `git diff --check` in both repositories.

No verification step applies Alembic, starts production services, registers a webhook, or contacts real integrations.
