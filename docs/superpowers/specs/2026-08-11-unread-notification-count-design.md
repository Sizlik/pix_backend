# Счётчик непрочитанных уведомлений

## Цель

Показывать авторизованному пользователю точное количество непрочитанных уведомлений возле пункта «Оповещения» в боковом меню и рядом с заголовком страницы уведомлений. Значение должно обновляться без перезагрузки страницы при создании и прочтении уведомлений и синхронизироваться между вкладками и backend-процессами.

## Область изменений

Изменения затрагивают backend `pix_backend` и соседний frontend `pix_frontend_v2`. Существующие таблица `notifications` и поле `is_readed` остаются источником истины; миграция базы данных не требуется. Список уведомлений и его обогащение сообщениями или данными заказа сохраняют текущий контракт.

## Backend-архитектура

### Подсчёт и операции чтения

`NotificationRepository` получает специализированные операции:

- посчитать непрочитанные уведомления конкретного пользователя через `SELECT count(...)`;
- пометить одно уведомление прочитанным только при совпадении `notification_id` и `user_id`;
- пометить все непрочитанные уведомления пользователя одним `UPDATE`.

`NotificationManager` координирует операции репозитория и публикацию нового счётчика. После успешного создания или чтения он заново получает абсолютное количество из PostgreSQL и публикует его. Абсолютное значение используется вместо событий `+1` и `-1`, чтобы повторная доставка, несколько вкладок и параллельные изменения не приводили к рассинхронизации.

Чтение чужого уведомления не изменяет данные и не влияет на счётчик текущего пользователя. Операции чтения остаются идемпотентными.

### REST-контракт

`GET /api_v1/notifications/unread-count` требует текущего пользователя и возвращает:

```json
{
  "unread_count": 3
}
```

`POST /api_v1/notifications/read/{id}` использует текущего пользователя при обновлении. `POST /api_v1/notifications/read` выполняет одну массовую операцию для текущего пользователя. Оба endpoint возвращают `{"unread_count": number}` и публикуют то же авторитетное значение по WebSocket. Чужой, отсутствующий или уже прочитанный ID обрабатывается идемпотентно и возвращает неизменившийся счётчик без раскрытия существования чужой записи.

### Канал реального времени

`WS /api_v1/notifications/ws?auth=<token>` использует ту же JWT/Redis-проверку, что и существующий WebSocket чата. Соединение привязывается только к ID аутентифицированного пользователя. Сразу после подключения сервер отправляет текущее значение:

```json
{
  "type": "notification_count",
  "unread_count": 3
}
```

Последующие сообщения имеют тот же формат и содержат абсолютное значение. Redis pub/sub с отдельным префиксом пользовательского канала доставляет событие всем backend-процессам, а локальный hub рассылает его всем соединениям пользователя.

Обычные пути создания уведомлений публикуют значение через `NotificationManager` после успешного commit. Уведомление сообщения по заказу создаётся вместе с сообщением в одной транзакции `OrderChatRepository`; соответствующий use case публикует изменение только после возврата из успешно завершённой транзакции. Ошибка транзакции не порождает WebSocket-событие.

Lifecycle FastAPI запускает и останавливает notification realtime рядом с существующим chat realtime. Обычные import, тесты и локальный старт при отключённых интеграциях не обращаются к production-сервисам.

## Frontend-архитектура

### Единое состояние dashboard

`NotificationCountProvider` размещается в dashboard layout и существует при переходах между защищёнными страницами. Он:

1. запрашивает `GET /notifications/unread-count` без фонового toast;
2. открывает notification WebSocket с bearer token;
3. принимает только валидные сообщения `notification_count` с неотрицательным целым значением;
4. повторно запрашивает значение при возврате фокуса на вкладку;
5. предоставляет компонентам текущее значение и безопасные операции локального обновления/повторной синхронизации.

При сетевом обрыве WebSocket переподключается с ограниченной увеличиваемой задержкой. После подключения сервер присылает актуальное значение, поэтому пропущенные события не накапливают ошибку. Закрытие с кодом `4401` прекращает автоматические попытки до новой авторизации.

Ошибка фонового запроса или WebSocket не показывает toast и не превращает неизвестное значение в ложный ноль. Последнее подтверждённое значение сохраняется; если ни одного значения ещё нет, числовой бейдж временно не отображается.

### Отображение

`Navbar` читает значение из общего provider. Возле колокольчика показывается компактный бейдж с точным числом; в свёрнутом меню он позиционируется поверх иконки и остаётся видимым. При нуле бейдж в меню скрывается.

Страница `/dashboard/notifications` показывает точное число рядом с заголовком «Оповещения». На этой странице ноль отображается явно.

### Прочтение

Непрочитанное уведомление помечается прочитанным и по наведению мыши, и по клику. Локальный признак меняется до завершения запроса, чтобы повторное событие hover/click не отправило второй запрос, а общий счётчик уменьшается ровно один раз. Кнопка «Прочитать всё» локально переводит все элементы в прочитанные и устанавливает счётчик в ноль.

После успешной операции WebSocket доставляет точное серверное значение во все вкладки. При ошибке frontend откатывает локальное состояние затронутых уведомлений и выполняет контрольный запрос счётчика. Существующий переход по клику на уведомления заказа сохраняется.

## Ошибки и граничные случаи

- Отсутствующий или недействительный WebSocket token закрывает соединение кодом `4401` без раскрытия данных.
- ID чужого или отсутствующего уведомления не изменяет записи и не уменьшает счётчик.
- Повторное прочтение уже прочитанного уведомления не меняет количество.
- Одновременные операции в нескольких вкладках сходятся к абсолютному значению из PostgreSQL.
- Значение всегда является неотрицательным целым числом; некорректное WebSocket-сообщение игнорируется.
- Нулевая выборка возвращает `{"unread_count": 0}`.

## Проверка

Backend-тесты покрывают:

- подсчёт только непрочитанных уведомлений текущего пользователя;
- защищённое и идемпотентное чтение одного уведомления;
- массовое чтение одним repository-вызовом;
- публикацию абсолютного значения после успешной записи и отсутствие публикации после ошибки;
- WebSocket-аутентификацию, начальное значение и Redis-доставку нескольким локальным соединениям.

Frontend-тесты покрывают:

- начальное значение в Navbar и заголовке страницы;
- скрытие navbar-бейджа при нуле и явный ноль в заголовке;
- единичное уменьшение по hover/click;
- обнуление по «Прочитать всё»;
- применение абсолютного WebSocket-обновления;
- откат и повторную синхронизацию после ошибки чтения;
- корректное поведение при обрыве и `4401`.

После финальных правок выполняются `powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1` в backend и `npm.cmd run check` во frontend согласно межрепозиторному API-контракту.
