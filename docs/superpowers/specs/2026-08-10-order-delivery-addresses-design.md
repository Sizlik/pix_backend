# Адресная книга и адрес доставки заказа — дизайн

## Контекст

Новый заказ создаётся на странице `pix_frontend_v2/src/app/dashboard/neworder/page.tsx` и отправляется в
`POST /api_v1/orders`. Backend создаёт товары и заказ покупателя непосредственно в МойСклад, но текущий payload
заказа не содержит адрес доставки. В PostgreSQL также нет адресной книги пользователя.

Нужно запрашивать адрес при каждом оформлении заказа, разрешить пользователю хранить любое количество адресов,
искать их по названиям и автоматически выбирать адрес, который использовался в последнем успешно созданном
заказе. Адреса должны быть доступны как в checkout, так и на отдельной странице личного кабинета.

МойСклад поддерживает строковый и структурированный адрес доставки заказа в полях `shipmentAddress` и
`shipmentAddressFull`. Выбранный адрес будет копироваться в конкретный заказ покупателя; основной адрес
контрагента в МойСклад меняться не будет. Источник: [МойСклад JSON API 1.2](https://dev.moysklad.ru/doc/api/remap/1.2/).

## Цели

1. Добавить принадлежащую пользователю адресную книгу без ограничения количества записей.
2. Поддержать создание, чтение, поиск по названию, редактирование и удаление адресов.
3. Требовать выбранный адрес при создании нового заказа.
4. Передавать снимок выбранного адреса в адрес доставки заказа покупателя МойСклад.
5. После успешного создания заказа делать выбранный адрес адресом по умолчанию.
6. Предоставить одинаковые правила и компоненты управления адресами в checkout и на странице «Мои адреса».
7. Не раскрывать и не позволять изменять адреса другого пользователя.

## Не входит в задачу

- Международные адреса: первая версия работает только с адресами в России.
- Подсказки ФИАС, DaData, Google Maps, геокодирование и проверка существования адреса во внешнем сервисе.
- Изменение `actualAddress` или другого основного адреса контрагента в МойСклад.
- Хранение всей адресной книги в дополнительных полях или пользовательском справочнике МойСклад.
- Изменение адреса уже созданного заказа через интерфейс Pix.
- Восстановление удалённых адресов и мягкое удаление.
- Перенос адресов между пользователями или общая адресная книга организации.

## Принятые продуктовые решения

- Форма структурированная, а не одно свободное текстовое поле.
- Страна всегда `Россия` и не показывается в форме.
- Обязательные поля: название, город/населённый пункт, улица и дом.
- Необязательные поля: индекс, корпус/строение, квартира/офис и комментарий курьеру.
- Названия уникальны у одного пользователя без учёта регистра и лишних пробелов.
- Адрес становится адресом по умолчанию только после успешного создания заказа в МойСклад.
- Полный CRUD доступен и в checkout, и на отдельной странице `/dashboard/addresses`.
- Поиск выполняется только по названию адреса.

## Модель данных

Добавляется таблица `address` со следующими полями:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID | Первичный ключ, генерируется приложением |
| `user_id` | UUID | Обязательный внешний ключ на `user.id`, удаление пользователя каскадно удаляет адреса |
| `name` | String(100) | Отображаемое название после удаления пробелов по краям |
| `normalized_name` | String(100) | Служебное нормализованное название, клиенту не возвращается |
| `city` | String(100) | Обязательное поле |
| `street` | String(200) | Обязательное поле |
| `house` | String(30) | Обязательное поле |
| `postal_code` | String(6), nullable | Ровно шесть цифр, если заполнено |
| `building` | String(30), nullable | Корпус или строение |
| `apartment` | String(30), nullable | Квартира или офис |
| `delivery_comment` | String(500), nullable | Комментарий курьеру |
| `last_used_at` | DateTime(timezone), nullable | Время последнего успешного заказа с этим адресом |
| `created_at` | DateTime(timezone) | Время создания на сервере |
| `updated_at` | DateTime(timezone) | Время последнего изменения на сервере |

`normalized_name` вычисляется только backend: пробелы по краям удаляются, последовательности пробельных символов
заменяются одним пробелом, результат приводится к регистронезависимой форме Unicode. Ограничение уникальности на
`(user_id, normalized_name)` является окончательной защитой от гонок. Все пользовательские текстовые поля
обрезаются по краям; пустая после обрезки обязательная строка отклоняется.

Отдельный флаг `is_default` в таблице не хранится. Адрес по умолчанию — существующий адрес пользователя с
максимальным `last_used_at`. Это исключает необходимость атомарно снимать флаг со всех остальных адресов.
При равных значениях порядок стабилизируется по `updated_at`, затем по `id`. Новый адрес имеет
`last_used_at = null`; frontend может выбрать его в текущем checkout, но backend не считает его адресом по
умолчанию до успешного заказа.

Страна не хранится в строке адреса: первая версия всегда формирует значение `Россия` на сервере. Переход к
международным адресам потребует отдельной миграции и нового продуктового решения.

Редактирование и физическое удаление локальной записи безопасны для истории: заказ МойСклад уже содержит снимок
адреса и не ссылается на локальный `address.id`.

## API адресной книги

Все endpoints используют существующую bearer-аутентификацию и работают только с адресами текущего пользователя.
Пути добавляются под общий префикс `/api_v1`.

### Список и поиск

```text
GET /api_v1/addresses?search=дом&limit=20&offset=0
```

- `search` необязателен, нормализуется по тем же правилам, что название, и ищет подстроку только в
  `normalized_name`.
- `limit` по умолчанию равен 20, допустимый диапазон — 1–100.
- `offset` по умолчанию равен 0 и не может быть отрицательным.
- Сначала идут адреса по `last_used_at DESC NULLS LAST`, затем по `updated_at DESC`, затем по `id`.
- `is_default` вычисляется относительно всей адресной книги пользователя, а не только текущей страницы поиска.

Ответ:

```json
{
  "items": [
    {
      "id": "f28a3f40-9e14-11f0-0a80-123400000001",
      "name": "Дом",
      "city": "Калининград",
      "street": "Ленинский проспект",
      "house": "10",
      "postal_code": "236000",
      "building": "корп. 2",
      "apartment": "15",
      "delivery_comment": "Позвонить за 10 минут",
      "is_default": true,
      "created_at": "2026-08-10T10:00:00Z",
      "updated_at": "2026-08-10T10:00:00Z",
      "last_used_at": "2026-08-10T11:00:00Z"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

### Создание

```text
POST /api_v1/addresses
Content-Type: application/json
```

```json
{
  "name": "Дом",
  "city": "Калининград",
  "street": "Ленинский проспект",
  "house": "10",
  "postal_code": "236000",
  "building": "корп. 2",
  "apartment": "15",
  "delivery_comment": "Позвонить за 10 минут"
}
```

Успешный ответ — `201` и созданный адрес. `last_used_at` остаётся `null`, а `is_default` остаётся `false`, если
адрес ещё не использован в успешном заказе.

### Редактирование

```text
PATCH /api_v1/addresses/{address_id}
Content-Type: application/json
```

Payload содержит одно или несколько изменяемых полей из payload создания. Пустой объект отклоняется как `422`.
Успешный ответ — `200` и обновлённый адрес. Редактирование не меняет `last_used_at`.

### Удаление

```text
DELETE /api_v1/addresses/{address_id}
```

Успешный ответ — `204` без тела. Если удалён адрес по умолчанию, следующим адресом по умолчанию автоматически
становится оставшийся адрес с максимальным `last_used_at`. Если использованных адресов больше нет, ни один адрес
не имеет `is_default: true`.

### Ошибки адресной книги

- Неверная форма, длина, пустое обязательное поле или неверный индекс: `422`.
- Уже существующее нормализованное название: `409` с
  `{"detail": {"code": "address_name_conflict", "message": "Address name already exists"}}`.
- Неизвестный, удалённый или принадлежащий другому пользователю адрес: `404` с
  `{"detail": {"code": "address_not_found", "message": "Address not found"}}`.

Одинаковый `404` для отсутствующего и чужого адреса не раскрывает существование данных другого пользователя.

## Создание заказа

Контракт `POST /api_v1/orders` получает обязательный `address_id`:

```json
{
  "address_id": "f28a3f40-9e14-11f0-0a80-123400000001",
  "order_items": [
    {
      "link": "https://example.com/product",
      "count": 2,
      "comment": "Чёрный"
    }
  ]
}
```

Последовательность серверного сценария:

1. Найти адрес по `address_id` и `user_id`. Чужой, отсутствующий или удалённый адрес вернуть как
   `404 address_not_found` до обращений к МойСклад.
2. Создать товары МойСклад существующим `ProductManager`.
3. Сформировать позиции и снимок адреса.
4. Создать заказ покупателя МойСклад через `CustomerOrderManager`.
5. Только после успешного ответа МойСклад записать текущее серверное время в `last_used_at` выбранного адреса.
6. Выполнить существующее Telegram-уведомление и вернуть созданный заказ.

`CustomerOrderManager.create_order_by_request` получает готовый объект адреса или отдельный тип снимка адреса и
добавляет в payload МойСклад:

- `shipmentAddress` — собранная читаемая строка: индекс, Россия, город, улица, дом, корпус/строение,
  квартира/офис;
- `shipmentAddressFull.postalCode` — только если индекс заполнен;
- `shipmentAddressFull.city`, `street`, `house`, `apartment` — соответствующие структурированные части;
- корпус/строение добавляется к `house` в однозначном читаемом формате, потому что отдельного продуктового поля в
  первой версии нет;
- `shipmentAddressFull.addInfo` — комментарий курьеру, если заполнен.

`shipmentAddressFull.comment` не используется для пользовательского комментария. Текущая интеграция Privoz
интерпретирует значение этого поля, начинающееся с `#`, как идентификатор заказа Privoz; поле остаётся
зарезервированным для этого существующего сценария.

Редактирование или удаление локального адреса после создания заказа не вызывает обновление МойСклад. Основной
адрес контрагента также не изменяется.

Если МойСклад не создал заказ, `last_used_at` не меняется, Telegram не отправляется, frontend сохраняет корзину и
выбор. Если заказ МойСклад уже создан, но вторичное локальное обновление `last_used_at` завершилось ошибкой,
backend не должен предлагать пользователю повторить создание и рисковать дубликатом заказа: успешный заказ
возвращается клиенту, а ошибка настройки адреса журналируется без персональных данных. При штатной работе
`last_used_at` обновляется до успешного ответа клиенту.

## Backend-архитектура

Новая функциональность следует существующим границам репозитория:

- `routes/addresses.py` отвечает за HTTP, зависимости, query-параметры и отображение доменных ошибок в HTTP;
- `dependecies/addresses.py` создаёт manager/repository для текущего запроса;
- `manager/addresses.py` содержит нормализацию, CRUD, выбор адреса по умолчанию и отметку использования;
- специализированный PostgreSQL repository отвечает за запросы, пагинацию, поиск и атомарные записи;
- `db/models/addresses.py` содержит SQLAlchemy-модель;
- `db/schemas/addresses.py` содержит Pydantic-схемы входа и ответа;
- `manager/moysklad.py` только добавляет снимок адреса к payload заказа МойСклад;
- `manager/order_creation.py` оркестрирует адрес, товары, заказ МойСклад, отметку использования и уведомление;
- `routes/orders.py` принимает транспортную схему и вызывает единый сценарий `OrderCreationManager`.

Route-функции не реализуют правила нормализации, выбора адреса по умолчанию или форматирования МойСклад payload.
Модель адреса импортируется в Alembic metadata. Новая миграция создаёт только таблицу, внешний ключ и индексы; она
не изменяет существующие строки и не выполняется агентом автоматически.

## Frontend UX

### Checkout

На странице `/dashboard/neworder` перед кнопками очистки и оформления появляется секция «Адрес доставки»:

- строка «Поиск по названию»;
- карточки найденных адресов с названием и собранной строкой адреса;
- метка «По умолчанию» у последнего использованного адреса;
- визуальное выделение текущего выбора;
- кнопки «Добавить», «Изменить» и «Удалить»;
- кнопка «Загрузить ещё», если `total > offset + items.length`.

При первой загрузке без поискового запроса выбирается элемент с `is_default: true`. Если использованных адресов
нет, адрес автоматически не назначается. После создания адреса из checkout он сразу добавляется и выбирается
локально, но метка «По умолчанию» появляется только после успешного заказа.

Если список пуст, показывается объяснение «Добавьте адрес доставки, чтобы оформить заказ» и основная кнопка
«Добавить адрес». Если поиск ничего не нашёл, показывается отдельное состояние «Адреса с таким названием не
найдены» без потери текущего выбора.

Кнопка «Оформить» недоступна, если корзина пуста, адрес не выбран или запрос уже выполняется. Нажатие отправляет
один запрос с `address_id`; повторное нажатие блокируется. После успеха корзина очищается и пользователь переходит
к списку заказов. При любой ошибке до подтверждённого создания заказа корзина и выбранный адрес остаются на
странице.

Если выбранный адрес удалён в другой вкладке, `404 address_not_found` приводит к обновлению списка, сбросу
устаревшего выбора и сообщению «Адрес был удалён. Выберите другой адрес».

### Форма адреса

Создание и редактирование используют один общий диалог с полями из модели. Поля помечают обязательность,
отображают серверные ошибки рядом с соответствующим вводом и не закрывают диалог при ошибке. Индекс принимает
ровно шесть цифр. Страна показана как неизменяемая подпись «Россия» либо не показывается; отдельного input нет.

Перед удалением всегда показывается подтверждение с названием адреса. После удаления выбранного адреса checkout
выбирает текущий адрес по умолчанию, если он есть; иначе оставляет выбор пустым.

### Страница «Мои адреса»

Добавляется `/dashboard/addresses` и пункт «Мои адреса» в защищённой навигации. Страница использует те же карточки,
форму, подтверждение удаления, серверный поиск и пагинацию, что checkout. Общие компоненты располагаются вне
страниц, чтобы правила отображения и доступности не расходились.

Поисковый запрос отправляется после задержки около 300 мс. Устаревший ответ не должен заменять результаты более
нового запроса. Поиск выполняется только по названию, как указано пользователю в placeholder.

## Конкурентность и согласованность

- Уникальный индекс является источником истины для конфликта названий; manager переводит нарушение в
  `address_name_conflict`.
- Любое чтение, обновление или удаление включает `user_id` в условие запроса.
- `is_default` определяется по всей адресной книге пользователя, поэтому поиск не меняет смысл метки.
- Два параллельных успешных заказа могут обновить разные адреса. По умолчанию становится адрес с наиболее поздним
  временем завершившегося локального обновления; это соответствует последнему успешно обработанному выбору.
- Удаление между загрузкой checkout и отправкой заказа безопасно завершается `address_not_found` до создания
  удалённого адреса в новом заказе.
- Ошибки внешней интеграции не откатывают и не удаляют саму адресную книгу.

## Миграция и выпуск

Миграция добавляет новую таблицу и не требует backfill. После выпуска существующий пользователь увидит пустую
адресную книгу и должен добавить адрес перед следующим заказом.

Изменение затрагивает общий API-контракт двух соседних репозиториев. Backend и frontend выпускаются
скоординированно: новая версия frontend всегда отправляет `address_id`, а backend считает его обязательным.
Перед применением миграции вручную проверяются активный URL базы, файл миграции и `alembic history`. Автоматический
`upgrade` в рамках реализации или тестов запрещён.

## Тестирование

Backend-тесты без рабочих внешних интеграций проверяют:

- нормализацию названия и текстовых полей;
- валидацию обязательных значений, длины и шестизначного индекса;
- CRUD, поиск-подстроку, пагинацию и стабильную сортировку;
- конфликт названий, включая регистр и повторные пробелы;
- полную изоляцию адресов разных пользователей;
- вычисление `is_default`, переход default после использования и поведение после удаления;
- обязательность `address_id` и ранний отказ для чужого/удалённого адреса;
- точный `shipmentAddress` и `shipmentAddressFull`, включая отсутствие пользовательского значения в `comment`;
- обновление `last_used_at` только после успешного ответа МойСклад;
- сохранение прежнего `last_used_at` при ошибке МойСклад;
- HTTP-контракты `201`, `204`, `404`, `409` и `422` с подменёнными зависимостями;
- корректность новой миграции и единственную голову истории Alembic.

Frontend unit-тесты проверяют:

- форматирование отображаемой строки адреса;
- выбор `is_default` при первой загрузке;
- локальный выбор только что созданного адреса;
- сброс или замену выбора после удаления;
- запрет оформления без корзины или адреса;
- payload заказа с `address_id`;
- защиту от устаревших результатов поиска.

Browser-тесты с локальным mock backend проверяют:

- создание первого адреса и оформление заказа с ним;
- автоматический выбор последнего использованного адреса при повторном входе;
- поиск, редактирование и подтверждённое удаление в checkout и на странице «Мои адреса»;
- сохранение корзины и выбора при ошибке создания заказа;
- сообщение и обновление списка при удалённом в другой вкладке адресе;
- отсутствие двойного запроса при повторном нажатии;
- пригодность интерфейса для mobile и desktop viewport.

Итоговая проверка после последних изменений: backend `scripts/check.ps1`, frontend `npm.cmd run check`,
`git diff --check`, ручной просмотр миграции и `alembic history`. Проверки не обращаются к рабочим МойСклад,
Telegram или другим внешним интеграциям.

## Критерии приёмки

1. Авторизованный пользователь может хранить любое количество российских структурированных адресов.
2. Названия уникальны для пользователя без учёта регистра и лишних пробелов.
3. Поиск на обеих страницах находит адреса по подстроке названия.
4. Пользователь не может прочитать, изменить, удалить или использовать в заказе чужой адрес.
5. Заказ нельзя оформить без выбранного адреса.
6. Новый заказ МойСклад содержит читаемый и структурированный снимок выбранного адреса доставки.
7. Основной адрес контрагента МойСклад не изменяется.
8. Последний успешно использованный адрес автоматически выбран при следующем оформлении.
9. Ошибка МойСклад не меняет адрес по умолчанию и не очищает корзину.
10. Редактирование или удаление локального адреса не меняет адрес старого заказа.
11. Checkout и страница «Мои адреса» используют одинаковые компоненты и правила CRUD.
12. Backend и frontend проверки проходят без обращений к рабочим внешним сервисам.
