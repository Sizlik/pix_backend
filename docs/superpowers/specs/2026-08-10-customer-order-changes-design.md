# Изменение подтверждённого заказа клиентом — дизайн

## Контекст

Страница заказа сейчас разрешает менять количество и удалять позиции только
при статусе `Ожидает подтверждения клиента`. Каждая такая правка немедленно
вызывает отдельный endpoint МойСклад. Изменение количества и удаление позиции
не меняют статус заказа и не отправляют уведомление в рабочую Telegram-группу.
Backend уже умеет добавлять позиции, но текущая страница заказа не предоставляет
клиенту соответствующий интерфейс.

Нужно разрешить клиенту изменять позиции после подтверждения магазина,
переводить реально изменённый заказ в статус `Изменен клиентом` и отправлять
одно Telegram-уведомление после сохранения всей серии правок.

## Цели

1. Разрешить клиенту добавлять и удалять позиции, а также менять их количество
   в явно определённых статусах заказа.
2. Накапливать правки на странице и применять их одной кнопкой
   `Сохранить изменения`.
3. Одним обновлением заказа в МойСклад заменить итоговый набор позиций и
   установить статус `Изменен клиентом`.
4. После успешного изменения отправить одно уведомление в рабочую
   Telegram-группу.
5. Проверять на backend владельца, актуальность версии и допустимость статуса,
   чтобы ограничения нельзя было обойти прямым API-запросом.
6. Сохранить безопасное поведение существующих endpoints отдельных операций.

## Не входит в задачу

- Редактирование названия или комментария уже существующей позиции.
- Изменение рассчитанной магазином цены со стороны клиента.
- Редактирование заказа после перехода в операционные статусы исполнения,
  доставки, выдачи, возврата, отмены или закрытия.
- Добавление очереди, outbox-таблицы или повторной доставки Telegram-сообщений.
- Миграции PostgreSQL.
- Изменение бизнес-процесса, которым сотрудники магазина повторно проверяют
  заказ со статусом `Изменен клиентом`.

## Разрешённые статусы

Редактирование разрешено только при одном из следующих точных имён статуса
МойСклад:

- `Подтвержден менеджером`;
- `Ожидает подтверждения клиента`;
- `Подтвержден клиентом`;
- `Изменен клиентом`.

Любой другой статус блокирует изменение. Таким образом, заказ перестаёт быть
редактируемым, когда магазин переводит его в следующий операционный статус,
например `Заказ принят` или `Принят к исполнению`. Проверка выполняется как в
интерфейсе, так и на backend; backend является источником истины.

## Пользовательский сценарий

### Загрузка страницы

Frontend получает заказ с полным списком позиций, статусом и полем `updated`
МойСклад. Если статус разрешён, таблица переходит в режим редактирования.
В остальных статусах таблица остаётся доступной только для просмотра.

### Локальные правки

В режиме редактирования клиент может:

- изменить количество существующей позиции на целое число больше нуля;
- удалить существующую или ещё не сохранённую новую позицию;
- добавить позицию с полями `Позиция`, `Количество`, `Комментарий`.

Комментарий новой позиции может быть пустым; позиция и количество обязательны.

Правки хранятся в состоянии страницы. Изменение ячейки, удаление и добавление не
вызывают запросы изменения заказа. Новая позиция получает временный локальный
идентификатор, который не передаётся как идентификатор МойСклад.

Пустой заказ сохранить нельзя. Если клиент хочет отказаться от единственной
позиции, он должен отменить весь заказ существующим действием отмены.

### Сохранение

Кнопка `Сохранить изменения` активна только при наличии фактической разницы с
загруженной версией. Пока есть несохранённые правки, подтверждение заказа
недоступно, чтобы клиент не подтвердил устаревший расчёт.

После успешного сохранения frontend заменяет локальные данные ответом backend,
обновляет версию, показывает статус `Изменен клиентом` и сбрасывает признак
несохранённых изменений. Заказ остаётся редактируемым, поэтому клиент может
внести и сохранить следующую серию правок до перевода магазином в другой
статус.

## API-контракт

Добавляется аутентифицированный endpoint:

```text
PUT /api_v1/orders/{order_id}/changes
Authorization: <existing bearer token>
Content-Type: application/json
```

Тело содержит версию, которую видел клиент, и полный желаемый набор позиций:

```json
{
  "expected_updated": "2026-08-10 12:34:56.789",
  "positions": [
    {
      "id": "8dd83620-9e15-11f0-0a80-123400000001",
      "count": 3
    },
    {
      "link": "https://example.com/product",
      "count": 1,
      "comment": "Цвет: чёрный"
    }
  ]
}
```

Существующая позиция определяется полем `id`; frontend не передаёт для неё
цену или ссылку на ассортимент. Новая позиция не содержит `id` и задаётся
полями `link`, `count`, `comment`. Существующая позиция текущего заказа,
отсутствующая в итоговом массиве, считается удалённой.

Успешный ответ:

```json
{
  "order": {
    "id": "f28a3f40-9e14-11f0-0a80-123400000001",
    "updated": "2026-08-10 12:36:10.123",
    "state": {"name": "Изменен клиентом"},
    "positions": {"rows": []}
  },
  "changed": true,
  "notification_sent": true
}
```

Для корректного no-op запроса backend возвращает `changed: false` и
`notification_sent: null`; статус и Telegram не затрагиваются. Если заказ
сохранён, но Telegram недоступен, ответ остаётся успешным и содержит
`changed: true`, `notification_sent: false`.

## Backend-архитектура

Route принимает транспортную схему, текущего пользователя и менеджеры через
`Depends`. Бизнес-последовательность находится в manager-слое, а обращения к
МойСклад остаются в repository-слое.

Менеджер пакетного изменения выполняет следующие шаги:

1. Получает свежий заказ с развёрнутыми `positions.assortment` и `state`.
2. Сравнивает идентификатор `agent` заказа с
   `user.moysklad_counterparty_id`. Чужой или недоступный заказ возвращается как
   `404`, чтобы не раскрывать его существование.
3. Проверяет точное имя статуса по разрешённому набору.
4. Сравнивает `expected_updated` с текущим `updated` заказа.
5. Проверяет непустой итоговый список, уникальность и принадлежность всех
   переданных идентификаторов существующих позиций, а также положительное целое
   количество.
6. Вычисляет разницу: добавленные, удалённые и изменённые по количеству
   позиции. При отсутствии разницы возвращает no-op ответ.
7. Создаёт товары МойСклад для новых позиций через существующий
   `ProductManager`.
8. Получает meta статуса `Изменен клиентом` из metadata заказа покупателя.
9. Строит полный массив позиций. Для существующих строк ассортимент, цена и
   остальные недоступные клиенту данные берутся из свежего ответа МойСклад;
   новые строки ссылаются на созданные товары.
10. Одним `PUT` заказа передаёт `positions` и `state`. Массив позиций полностью
    заменяет набор позиций документа; совпадающие идентификаторы обновляются,
    отсутствующие удаляются, новые добавляются.
11. После успешного обновления отправляет одно Telegram-сообщение и возвращает
    обновлённый заказ.

Создание товаров для новых строк предшествует обновлению заказа, поскольку
позиции должны ссылаться на существующий ассортимент. Если итоговое обновление
заказа не выполнится, созданные товары могут остаться неиспользованными. Это
существующее свойство интеграции и приемлемый компромисс без распределённой
транзакции между ресурсами МойСклад.

Сравнение `expected_updated` является оптимистической предварительной защитой
от перезаписи изменений магазина. Позиции и новый статус записываются одним
запросом, но интеграция не обещает строгой блокировки изменения, которое
произойдёт в коротком интервале между контрольным чтением и записью.

## Совместимость существующих endpoints

Frontend перестаёт вызывать немедленные endpoints изменения количества,
удаления и добавления позиции. Они остаются доступными для совместимости, но
переводятся на общий manager-сценарий:

- проверяют владельца и разрешённый статус;
- строят итоговый набор из свежего заказа;
- не позволяют удалить последнюю позицию;
- одним обновлением меняют позиции и статус на `Изменен клиентом`;
- отправляют рабочей группе уведомление после успешной фактической правки.

Таким образом, старый API нельзя использовать для обхода статуса или
Telegram-уведомления. Пакетный frontend-сценарий остаётся единственным способом
получить одно сообщение на серию пользовательских правок.

## Telegram-уведомление

Сообщение отправляется через существующий `telegram_sender` в `CHAT_ID` и
содержит:

- безопасную HTML-ссылку на заказ МойСклад;
- имя клиента и его номер;
- число добавленных позиций;
- число удалённых позиций;
- число позиций с изменённым количеством;
- новый статус `Изменен клиентом`.

Данные клиента экранируются перед вставкой в HTML. Уведомление отправляется
только после успешного изменения МойСклад. Ошибка Telegram не откатывает уже
сохранённый заказ и не превращает ответ в ошибку сохранения: backend возвращает
`notification_sent: false`, а frontend показывает предупреждение без повторной
отправки заказа.

## Ошибки и конкурентные изменения

- Неверная форма payload, пустой итоговый список, неположительное или нецелое
  количество, повторяющийся либо неизвестный position id: `422`.
- Заказ не принадлежит текущему пользователю или недоступен: `404`.
- Текущий статус не разрешает редактирование:
  `409` с кодом `order_not_editable`.
- `updated` не совпадает с `expected_updated`:
  `409` с кодом `order_version_conflict`.
- Ошибка чтения, создания товара или обновления заказа в МойСклад: сохранение
  считается неуспешным; Telegram не отправляется, frontend сохраняет локальные
  правки и позволяет повторить попытку.
- Ошибка Telegram после успешного изменения: успешный ответ с
  `notification_sent: false` и предупреждение пользователю.

При `order_version_conflict` frontend не смешивает серверную и локальную версии
автоматически. Он сохраняет правки в памяти, предупреждает пользователя и
предлагает загрузить актуальный заказ. При `order_not_editable` frontend
загружает актуальный заказ в режиме просмотра.

## Frontend-архитектура

API-клиент в `src/routes/routes.tsx` получает типизированную функцию пакетного
сохранения. Страница заказа хранит отдельно исходный снимок и редактируемые
строки, чтобы вычислять dirty-состояние и формировать полный payload.

Логику разрешённых статусов и построения payload следует вынести в небольшие
чистые функции рядом со страницей, чтобы их можно было покрыть unit-тестами без
AG Grid и сетевых запросов. Существующий визуальный стиль формы новой позиции,
таблицы и `PixButton` сохраняется. Отдельная сложная форма или новый глобальный
state manager не нужны.

После успешного ответа таблица заполняется возвращённым заказом, а не
предполагаемым локальным результатом. Это даёт клиенту созданные МойСклад id,
рассчитанные поля и актуальный `updated`.

## Тестирование

Backend-тесты с подменёнными manager/repository/Telegram зависимостями
проверяют:

- разрешение ровно четырёх согласованных статусов и блокировку любого другого;
- отказ для чужого заказа;
- добавление, удаление и изменение количества по отдельности и в одном запросе;
- запрет пустого заказа, нецелого/неположительного количества, неизвестных и
  повторных id;
- no-op без смены статуса и Telegram;
- конфликт `expected_updated`;
- создание полного массива позиций из серверных данных;
- одно обновление заказа с позициями и статусом;
- одно Telegram-сообщение со сводкой после успешного пакетного изменения;
- отсутствие Telegram при ошибке МойСклад;
- успешное сохранение с `notification_sent: false` при ошибке Telegram;
- те же ограничения для совместимых endpoints отдельных операций;
- HTTP-контракт нового endpoint без внешних сетевых вызовов.

Frontend unit-тесты проверяют:

- вычисление права редактирования;
- dirty-состояние;
- добавление, удаление и изменение количества в итоговом payload;
- запрет пустого набора;
- отсутствие немедленных mutation-запросов при редактировании таблицы.

Browser-тест с локальным mock backend проверяет полный сценарий: открыть заказ в
разрешённом статусе, изменить количество, удалить и добавить позицию, увидеть
одну активную кнопку сохранения, отправить один batch-запрос, получить статус
`Изменен клиентом` и обновлённую таблицу. Отдельные сценарии проверяют
read-only режим, конфликт версии и предупреждение при
`notification_sent: false`.

Проверки backend и frontend не обращаются к рабочим МойСклад или Telegram.

## Критерии приёмки

1. В четырёх разрешённых статусах клиент может локально добавить, удалить и
   изменить количество позиций.
2. В любом другом статусе UI не показывает редактирование, а backend отклоняет
   mutation-запрос.
3. Последнюю позицию удалить и сохранить нельзя.
4. До нажатия `Сохранить изменения` МойСклад и Telegram не изменяются.
5. Одна серия правок создаёт один batch-запрос, одно обновление заказа и не
   более одного Telegram-сообщения.
6. После фактической правки заказ получает статус `Изменен клиентом` и остаётся
   редактируемым.
7. No-op не меняет статус и не отправляет Telegram.
8. Устаревшая версия или сменившийся статус не перезаписываются молча.
9. Ошибка Telegram не предлагает клиенту повторно применять уже сохранённые
   изменения.
10. Backend `scripts/check.ps1` и frontend `npm.cmd run check` проходят без
    внешних интеграционных вызовов.
